# RoboMaster 上下位机串口联调记录

> 深北莫北极熊战队 RoboMaster 项目，上位机 ROS2 Humble ↔ 下位机 STM32 串口通信。
> 本文完整记录从获取 GitHub 源文件到链路打通的全部工作、协议细节、踩坑与验证方法，供后续维护查阅。
> 最后更新：2026-08-16

---

## 1. 项目概览

| 角色 | 工程 | 说明 |
|---|---|---|
| 上位机 | `standard_robot_pp_ros2`（ROS2 Humble 串口驱动） | GitHub `SMBU-PolarBear-Robotics-Team`，commit `e5af8d2` |
| 接口 msg | `pb_rm_interfaces` | commit `66c8bee`，裁判系统 msg 定义 |
| 下位机 | `StandardRobotpp`（STM32 电控） | **协议权威源**，最新 Gitee 2026-04-08 |

- 串口帧头 **SOF = 0x5A**（DJI 标准）。
- 上下位机底层帧格式、SOF、CRC8/CRC16 算法**两边完全一致、同源**。
- 最终结论：问题从来不在于协议层，而在于「topic 没对上」和「串口缓冲区残留」（详见第 2 节历程、第 11 节踩坑）。

## 2. 完整工作历程（从获取源文件至今）

按时间顺序，分六个阶段。每一阶段记录：目标、做了什么、发现了什么、怎么处理。

- 拉取上位机驱动 `standard_robot_pp_ros2`（GitHub `SMBU-PolarBear-Robotics-Team`，commit `e5af8d2`）。

### 阶段二：搭建 / 整理 colcon workspace

目标：让上位机在 minipc 上能 `colcon build` + `ros2 launch` 跑起来。

1. workspace 定在 `/home/ew/text/EEEWW`（从 `/home/ew/EEEWW` 移动过来）。
2. **修移动残留问题（两类）**：
   - `install/` 里的文本文件仍写着旧路径 `/home/ew/EEEWW` → 用 `sed` 全局替换成 `/home/ew/text/EEEWW`；
   - `install/` 里有 **505 个软链接**（`package.xml`、`local_setup.bash`、`.so` 库）指向旧路径，`sed` 改不到软链接 → 用 `ln -sfn` 把前缀 `/home/ew/EEEWW` 重指到 `/home/ew/text/EEEWW`。
   - 不修的话：`source` 报 14 个包 not found、launch 报 package not found。
3. **修断链**：
   - `EEEWW/src/pb_rm_interfaces` → 指回 `/home/ew/text/pb_rm_interfaces`；
   - `auto_aim_interfaces` → 指回 `/home/ew/ros_ws/src/auto_aim_interfaces`；
   - `robot_stm32_bridge` 仍断链（原指向已删除的目录，非上位机依赖，忽略）。
4. 确认 `serial_driver` 是 apt 装的（`ros-humble-serial-driver`）。

### 阶段三：确认通信硬件与串口参数

目标：搞清楚到底接哪个串口、参数怎么传。

1. 排查串口口，确认关键事实：
   - **上位机通信口 = C 板原生 USB CDC（`/dev/ttyACM0`，VID:PID `0483:5740`），不是 CH340**。
   - CH340（`/dev/ttyUSB0`，`1a86:7523`）对应 C 板 Uart2（USART1），发的是 SOF=0xA5 的遥控器/云台协议，上位机接它会**收不到 0x5A 数据**。
2. 确认串口参数（`config/standard_robot_pp_ros2.yaml`）：`device_name: /dev/ttyACM0`、`baud_rate: 115200`、`stop_bits: "1"`。
3. 发现传参坑：`stop_bits` 是 string 类型，命令行必须 `-p 'stop_bits:="1"'` 单引号保住，否则 `"1"` 被解析成 int → `InvalidParameterType`。

### 阶段四：串口协议对齐分析（仅分析，未动工）

目标：确认上位机能否正确解析下位机发的所有数据包。

1. 逐字段对比上位机 `packet_typedef.hpp` 与下位机 `usb_typdef.h`，发现两处问题：
   - **数据段 id 映射错位**；
   - **多个结构体字段与下位机最新版（2026RMUL / 裁判系统 V1.7.0）不一致**。
2. 整理出下位机实际发送的 **14 个包**，并写出 id 重映射表：

   | 常量 | 上位机现值 | 应改为 | 备注 |
   |---|---|---|---|
   | ID_GAME_STATUS | 0x07 | **0x04** | |
   | ID_EVENT_DATA | 0x04 | **0x07** | |
   | ID_REFEREE_WARNING | — | **新增 0x08** | |
   | ID_ROBOT_STATUS | 0x0B | **0x0A** | |
   | ID_RFID_STATUS | 0x0A | **0x11** | |
   | ID_SHOOT_DATA | — | **新增 0x0F** | |
   | ID_GROUND_ROBOT_POSITION | 0x09 | **0x13** | |
   | ID_JOINT_STATE | 0x0C | **0x1D** | |
   | ID_ROBOT_MOTION | 0x08 | **0x1E** | |
   | ID_PID_DEBUG | 0x05 | **删除** | 下位机不再发 |

   不变：ID_DEBUG(0x01)、ID_IMU(0x02)、ID_ROBOT_STATE_INFO(0x03)、ID_ALL_ROBOT_HP(0x06)、ID_BUFF(0x0D)、ID_ROBOT_CMD(0x01，下行发送方向)。

3. 联网查两个位域定义（Event 高 16 位、RfidStatus 扩展字节 `rfid_status_2`）未果，决定保守处理（原样接收、暂不发布、不臆想）。
4. 产出 plan 文件 `linear-orbiting-crane.md`，**但未改任何代码**——因为随后发现链路问题不在协议层，此份改动暂缓。

### 阶段五：排查 CRC8 error

1. 现象：节点启动时上报 `CRC8 error`。
2. 排查过程：怀疑读到的帧错位，追溯到串口缓冲区——下位机持续往外发帧，无人读取时，Linux 内核缓冲区积压了**半截帧**。
3. 结论：节点打开串口后第一次 read 恰好从一帧中间切开，导致 CRC8 校验失败。属**一次性错位**，干净重启后 0 错误。

### 阶段六：打通下行链路（cmd_vel → speed_vector）

目标：让上位机发的速度指令真正到达下位机 `ROBOT_CMD_DATA.speed_vector`。

1. **逐字节验证上位机发送正确**：结构体对齐、CRC8（`0x7f`）、CRC16 全部核对无误。
2. **strace 抓帧**确认串口确实在写：抓到 `5a 2b 01 7f | 89 7e 00 00 | ...`（详见第 12 节）。
3. 用户报告「`ros2 topic echo` 看得到速度，但 Keil 里 speed_vector 没变化」。
4. **Keil 断点验证下位机收到了帧**：`USB_RX_BUF`（地址 `0x2000A618`）开头有 `5A 2B 01 7F`，三个断点（找 SOF → CRC 校验 → memcpy 成功）全部命中。说明**上行链路正常**，问题在上位机「有没有数据可发」。
5. **定位根因**：完整 launch `standard_robot_pp_ros2.launch.py` **没有 cmd_vel remap**，节点订阅了空的 `/cmd_vel`（Publisher count=0）；而数据发在 `/red_standard_robot1/cmd_vel`（Publisher count=2）。订阅错 topic → 收不到速度 → speed_vector 恒为 0。
6. **新建 `launch/serial_only_launch.py`**（本工程唯一的代码改动），做三件事：
   - 启动前 `timeout 1 cat <device> > /dev/null` 清缓冲区（治 CRC8 error）；
   - `OnProcessExit` 保证清完缓冲再开串口节点；
   - `remappings=[("cmd_vel", cmd_vel_topic)]` 订阅重定向到 `/red_standard_robot1/cmd_vel`（治根因）。
7. **最终验证**：strace 解析出 speed_vector 非零（`vx=0.1677, vy=-0.9858, wz=3.1400`），用户在 Keil 确认 `ROBOT_CMD_DATA.speed_vector` 跟随变化，**端到端链路彻底打通**。

### 改动汇总

全程**只新建了 `serial_only_launch.py` 一个文件**。上下位机核心代码、msg、协议结构体**零改动**。真正的问题是「topic 没对上」+「串口缓冲区残留」，都不在协议层。

## 5. 串口协议帧格式

```
┌──────┬─────┬─────┬──────┬────────────┬───────────────┬───────┐
│ SOF  │ len │ id  │ crc8 │ time_stamp │     data      │ crc16 │
│ 1B   │ 1B  │ 1B  │ 1B   │    4B      │  (len-4) 字节 │  2B   │
│ 0x5A │     │     │      │            │               │       │
└──────┴─────┴─────┴──────┴────────────┴───────────────┴───────┘
└────────── 帧头 frame_header ──────────┘
```

- **len** = `time_stamp(4) + data` 的字节数（不含 crc16）。
- **crc8**：校验 `len + id` 两个字节（见第 6 节）。
- **crc16**：校验 `time_stamp + data`。
- id 唯一标识包类型；同一 id 在下行（命令）和上行（反馈）含义不同。

## 6. CRC 校验

### 6.1 CRC8（帧头）

- 多项式 `G(x)=x8+x5+x4+1`（0x31），查表法。
- `CRC8_INIT = 0xff`。
- 表首行：`0x00, 0x5e, 0xbc, 0xe2, 0x61, 0x3f, ...`（与下位机 `components/support/CRC8_CRC16.c` 完全同源）。
- 实现：`include/standard_robot_pp_ros2/crc8_crc16.hpp` → `crc8::get_CRC8_check_sum`。

### 6.2 CRC16（数据段）

- `CRC16_INIT = 0xffff`，查表法，表首行 `0x0000, 0x1189, 0x2312, ...`。
- 追加时**低字节在前**：`buf[n-2]=crc&0xff; buf[n-1]=crc>>8`。

> 排查时曾用 Python 位运算实现（MAXIM 变体）验证，与查表实现结果对不上（0x34 vs 0x7f）而误判 CRC 错误。**结论：两边查表同源，以查表为准，不要用位运算变体去对**。

## 7. 下行协议（上位机 → 下位机）：RobotCmd（id=0x01）

下位机接收并执行速度/云台/发射等控制指令。帧共 **49 字节**：

```
5A | 2B | 01 | 7F | time_stamp(4B) | data(39B) | crc16(2B)
```

`data` 结构（对齐下位机 `custom_typedef.h` 的 `RobotCmdData_t`）：

| 字段 | 类型 | 字节偏移 | 说明 |
|---|---|---|---|
| speed_vector.vx | float | 0–3 | x 方向速度 m/s |
| speed_vector.vy | float | 4–7 | y 方向速度 m/s |
| speed_vector.wz | float | 8–11 | 旋转速度 rad/s |
| chassis.roll | float | 12–15 | |
| chassis.pitch | float | 16–19 | |
| chassis.yaw | float | 20–23 | |
| chassis.leg_length | float | 24–27 | |
| gimbal.pitch | float | 28–31 | |
| gimbal.yaw | float | 32–35 | |
| shoot.fire | uint8_t | 36 | |
| shoot.fric_on | uint8_t | 37 | |
| tracking | bool | 38 | |

对应结构体：上位机 `packet_typedef.hpp` 的 `SendRobotCmdData`，下位机 `usb_typdef.h` 的 `ReceiveDataRobotCmd_s`（id 常量 `ROBOT_CMD_DATA_RECEIVE_ID = 0x01`）。

**数据流向**（下位机 `usb_task.c`）：
```
USB_Receive → 找 SOF → CRC8 校验 → CRC16 校验 → id 匹配 0x01
           → memcpy 到 RECEIVE_ROBOT_CMD_DATA
GetCmdData → RECEIVE_ROBOT_CMD_DATA.data.speed_vector → ROBOT_CMD_DATA.speed_vector
```

**关键细节**：`RECEIVE_ROBOT_CMD_DATA.data.speed_vector` 有 `.data`，而全局 `ROBOT_CMD_DATA.speed_vector` 没有 `.data`（`RobotCmdData_t` 里 speed_vector 是顶层字段）。

## 9. 启动方式

### 9.1 专用最小启动（推荐，已 remap cmd_vel）

```bash
# 实车（默认，不用加参数）
ros2 launch standard_robot_pp_ros2 serial_only_launch.py
```

**默认订阅 `/cmd_vel`（实车导航的命名空间）**。跑 gazebo 仿真时要覆盖回仿真命名空间：

```bash
# gazebo 仿真（数据发在 /red_standard_robot1/cmd_vel）
ros2 launch standard_robot_pp_ros2 serial_only_launch.py cmd_vel_topic:=/red_standard_robot1/cmd_vel

# 换串口设备（一般不用，默认 /dev/ttyACM0）
ros2 launch standard_robot_pp_ros2 serial_only_launch.py device_name:=/dev/ttyUSB0
```

`serial_only_launch.py` 做三件事：
1. 启动前 `timeout 1 cat <device> > /dev/null` 清空串口积压缓冲区；
2. 用 `OnProcessExit` 保证清完缓冲再开串口节点；
3. `remappings=[("cmd_vel", cmd_vel_topic)]` 把订阅重定向到 `cmd_vel_topic`（默认 `/cmd_vel`）。

**运行前提**：下位机 USB 必须已插好并上电，`ls /dev/ttyACM0` 有输出（`lsusb` 能看到 `0483:5740`），否则报 `Open serial port failed: No such file or directory`。

### 9.2 完整 launch（注意：无 cmd_vel remap）

```bash
ros2 launch standard_robot_pp_ros2 standard_robot_pp_ros2.launch.py
```

会拉起 joint_state_publisher / robot_state_publisher / serial 节点 / gimbal_manager，但**没有 cmd_vel remap**，节点订阅裸 `/cmd_vel`，收不到 `/red_standard_robot1/cmd_vel`（这就是"看不到速度"的根因）。

## 11. 踩坑记录

### 坑 1：CRC8 error（启动时报一次）
- **现象**：节点启动时报 `CRC8 error`。
- **原因**：下位机一直发、无人读，内核串口缓冲区积压半截帧；节点开串口第一次 read 从帧中间切开。
- **解决**：开串口前先清缓冲区（`serial_only_launch.py` 内置）。干净重启后 0 错误。

### 坑 2：cmd_vel 订阅错 topic（"看不到速度"的根因）
- **现象**：`ros2 topic echo` 能看到速度，但 Keil 里 `speed_vector` 一直是 0。
- **排查**：断点验证下位机**确实收到了帧**（USB_RX_BUF 有 `5A 2B 01 7F`，三个断点全命中），说明上行链路正常，问题在上位机「有没有数据可发」。
- **根因**：完整 launch 无 remap，节点订阅空 `/cmd_vel`（Publisher count=0）；数据发在 `/red_standard_robot1/cmd_vel`（Publisher count=2）。
- **解决**：用 `serial_only_launch.py`（已 remap）。

### 坑 3：两个节点进程同时占用串口
- **现象**：数据被瓜分、解析错乱。
- **解决**：`ps -ef | grep standard_robot` 排查，kill 多余进程，只留一个。

### 坑 4：strace 抓不到串口写入
- **原因**：① write 发生在 `sendData()` 子线程，需加 `-f`；② 节点重启后 fd 会变（16→19→20）。
- **正确姿势**：`strace -f -e trace=write -xx -s 200 -p PID`，用 `grep 'write('` 而非固定 fd。

### 坑 5：上位机 time_stamp 从未赋值（隐藏 bug，未修）
- `sendData()` 里只设了 `frame_header.len`，**从未给 `time_stamp` 赋值**。
- 后果：下位机 `RECEIVE_TIME` 停止更新、`USB_OFFLINE` 可能误判离线；但不影响 speed_vector 的 memcpy，速度链路照常工作。
- 状态：**待修**（需与下位机确认 time_stamp 语义后再补）。

### 坑 6：串口口选错
- 接 CH340（`/dev/ttyUSB0`，SOF=0xA5）收不到 0x5A 数据；必须接 C 板原生 USB CDC（`/dev/ttyACM0`）。

### 坑 7：Python 位运算 CRC 验证误报
- 用 MAXIM 变体位运算实现对 CRC 结果，与查表实现不一致，误判 CRC 错误。以两边同源查表为准。

### 坑 8：实车导航雷达 IP 配错
- **现象**：livox driver 报 `Can not get index` / `Storage point data failed`，点云出不来。
- **原因**：`pb2025_nav_bringup/config/reality/mid360_user_config.json` 里雷达 IP 写成 `192.168.1.119`，实际雷达 IP 是 `192.168.1.3`。
- **解决**：改为 `192.168.1.3`（已修复，源码 + install 都改了）。

### 坑 9：point-lio 重力参数不一致
- **现象**：`pointlio_mapping` 崩溃（`exit code -6` / SIGABRT）。
- **原因**：`nav2_params.yaml` 里 `gravity` / `gravity_init` 的 y 分量是 `0.5305...`，与能正常跑的 ros_ws 不一致（应为 `0.0`）。
- **解决**：改为 `0.0`（已修复）。

### 坑 10：ros_ws 残留导航抢雷达（实车导航连锁崩溃）
- **现象**：EEE 跑实车导航 `rm_navigation_reality_launch.py` 时，`livox`（SIGBUS）、`point_lio`（SIGABRT）、`slam_toolbox`（SIGSEGV）连锁崩溃。
- **原因**：MID-360 是网络雷达，ros_ws 的导航还在跑、livox driver 占着雷达 UDP 端口（56100~56500），两套 driver 同时连雷达冲突。
- **解决**：先彻底停掉 ros_ws 那套导航（`Ctrl+C` 或 kill），再跑 EEE 导航。排查命令：`ps -ef | grep -E 'ros_ws/install|livox'`。

### 坑 11：下位机 USB 没接
- **现象**：串口节点 `Open serial port failed: No such file or directory`，一直重试。
- **原因**：下位机（STM32 C 板）没上电/没插 USB，`/dev/ttyACM0` 不存在。
- **解决**：插好 USB + 上电，`ls /dev/ttyACM0` 确认出现（`lsusb` 有 `0483:5740`）。

## 12. 验证方法

### 12.1 上位机发送验证（strace）

```bash
sudo strace -f -e trace=write -xx -s 200 -p <node_pid> 2>&1 | grep 'write('
```

抓到的 RobotCmd 帧应为（速度非零时）：

```
5a 2b 01 7f | 89 7e 00 00 | 1e bf 2b 3e | a6 5f 7c bf | c3 f5 48 40
  帧头       time_stamp      vx          vy          wz
```

解析（IEEE754 小端）：`vx=0.1677, vy=-0.9858, wz=3.1400`。

### 12.2 下位机接收验证（Keil 断点）

- 三个断点：找 SOF → CRC8+CRC16 校验通过 → `memcpy` 到 `RECEIVE_ROBOT_CMD_DATA`。
- Memory 窗口看 `0x2000A618`（USB_RX_BUF），开头应是 `5A 2B 01 7F`。
- Watch 窗口**不实时刷新**，需手动暂停/刷新看 `ROBOT_CMD_DATA.speed_vector.vx/vy/wz`。
- 最终判据：推杆 → 三个值跟着变，松杆 → 归零。

### 12.3 确认订阅状态

```bash
ros2 node info /standard_robot_pp_ros2   # 看 Subscriptions 是否含 /red_standard_robot1/cmd_vel
ros2 topic echo /red_standard_robot1/cmd_vel
```
